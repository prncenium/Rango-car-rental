# 05.5 — Admin Panel

Status: DRAFT — for review before any code.
Reads: `specs/01-domain-and-state-machines.md`, `specs/02-api-contract.md`, `specs/03-auth-and-roles.md`, `specs/04-business-logic.md`.
Feeds: `tasks/01-implementation-plan.md` — a new `ADM-UI` block, and the `CL` (client) block for shared components.

**Scope.** Car **rental only**. No sale, no resale, no buyer, no offer, no negotiation, no ownership transfer — same permanent exclusion as every other spec in this set. **No online KYC and no document verification of any kind.** No document upload, no review queue, no verification status. Identity and licence checks happen entirely offline, in person, at handover, and are recorded as a checkbox and free text — never a file. This document does not reopen any of that; it builds the admin surface for the model specs 01–04 already settled.

## Authority

This document is written against the **fully-resolved** domain model — that is, specs 01–03 **as amended by spec 04's conflict resolutions** (its §CONFLICTS WITH EARLIER SPECS, X-A/X-B/X-C/X-D tables), which is itself the newest and most authoritative layer in this set. Where an earlier spec's literal text disagrees with spec 04's resolution, this document follows spec 04. Concretely, every screen below assumes:

| Assumption | Source | Consequence for this document |
|---|---|---|

There is **no `drivingLicence.imageUrl`** (spec 03 §5.3/§5.5 is overridden by spec 04 X-C1 — image fields are deleted). | Spec 04 §X-A1–X-A11, §5; spec 03 §5 as narrowed | §6.1 has no listing moderation lever tied to identity. §5.7 records a checkbox + typed number, never a file. |

Where this document needs an endpoint, field, or guard that no existing spec defines, it is marked **NEW — proposed by this spec** and numbered continuing the existing sequence (the highest endpoint number in specs 02–04 is `E-90`; new endpoints here start at `E-91`).

## 0. Conventions used throughout this document

### 0.1 Wireframe legend

Wireframes are ASCII box sketches. `[ Button ]` is an action; `<select>`/`<input>` are form controls; `▾` marks a dropdown; a row of `─` is a table divider; `≡` marks a queue/list row that opens a detail view on click.

### 0.2 Action-table columns

Every action listed under every screen carries, in this fixed order:

- **Endpoint** — the exact method, path, and `E-NN` id from specs 02/03/04, or `E-9N — NEW` if this document proposes it.
- **Transition** — the `entity: from → to` edge from spec 01 (as amended) it triggers, or `NONE` for a read.
- **Guards** — the named guard functions from spec 02 §12 / spec 04, verbatim where they exist.
- **Empty / Loading / Error states** — what the screen shows with zero rows, while the request is in flight, and for each realistically reachable error code from spec 02 §3.2/§3.3.

### 0.3 Standard error-state language, so it is not repeated at every single action

Unless an action's table overrides it, every mutating action in this document uses this common error presentation, matching spec 02 §3's error contract:

| Code | Admin-UI presentation |
|---|---|
| `400 VALIDATION_FAILED` | Inline field errors from `details.fieldErrors`; submit button stays disabled until resolved. Never a toast alone — the offending field is highlighted. |
| `401 UNAUTHENTICATED` | Full-screen re-authenticate interstitial; the in-flight action is discarded, not silently retried. |
| `403 FORBIDDEN` | "You don't have permission for this" toast; row/action disabled going forward for this session without a refresh. |
| `403 ACCOUNT_INACTIVE` | Full-screen "Your account has been deactivated" interstitial, forces logout — this should not normally be reachable by an admin acting on their own session mid-task, but the client must handle it (a `SUPER_ADMIN` can deactivate an `ADMIN` mid-session, §7.5). |
| `403 FORBIDDEN_TRANSITION` | "This action isn't available for this record" toast; UI re-fetches the record so stale `availableActions[]` do not offer it again. |
| `404 NOT_FOUND` | "This record is no longer available" toast; row is optimistically removed from the current list (see §9's rollback rule) and the queue re-fetches. |
| `409 INVALID_TRANSITION` | "This record has already changed" toast with `details.from`/`details.to`; row re-fetched and re-rendered in its current state — never silently retried. |
| `409 GUARD_FAILED` | A named, specific message keyed off `details.guard` (spec 02 §3.1: *"the admin UI can say 'cannot activate: payment not settled' instead of '409'"*) — every guard used below has its own copy, listed per action. |
| `409 CONFLICT` | Field- or reason-specific (e.g. `DATES_UNAVAILABLE` shows the conflicting days on the calendar inline). |
| `429 RATE_LIMITED` | "Too many actions, try again in Ns" using `Retry-After`; the action button is disabled for that window. |
| `500 INTERNAL` / `503 SERVICE_UNAVAILABLE` | Generic retry toast with the `requestId` shown in small print, for support correlation. |

### 0.4 Confirmation modal + mandatory reason — what the API actually requires vs. what the brief asks for

The brief's Section 7 requirement ("every state-changing action: confirmation modal + mandatory reason field") is a **UI-level policy this document adopts uniformly**, but it is stricter than the API contract in several places. The API's own `reason` requirement is inconsistent by design — spec 02/03/04 make `reason` mandatory on *destructive or adversarial* transitions (reject, delist, cancel, terminate, deactivate, no-show-clear, deposit-retain, password-reset) and only *optional* (`note?`) on *affirmative* ones (approve, publish, confirm, activate override, complete, reactivate). This document resolves the gap once, here, rather than re-litigating it on every action below:

> **RULE ADM-1 (this document).** Every state-changing admin action shows a confirmation modal. Where the underlying DTO's `reason`/`note` field is optional, the admin UI **still requires non-empty free text before the confirm button enables**, and sends it as `note` (or the endpoint's equivalent optional field). This is a client-side policy, not a server-side one — the server continues to accept `note` as optional for these endpoints, per their DTOs, so this UI convention **imposes no spec change** and cannot be bypassed by a non-UI API caller. **OPEN QUESTION ADM-OQ-1**: should specs 02/03/04 instead be amended to make `note` required at the schema level on every admin transition (closing the gap at the server rather than the client)? Doing so is a breaking DTO change on E-29, E-31, E-39, E-42, E-60 and needs its own amendment round; this document does not make that change and flags it rather than doing it silently, per `CLAUDE.md`'s "never modify specs while implementing".

Each action table below marks its reason/note field **[server-required]** or **[server-optional, UI-required per RULE ADM-1]** so the distinction stays visible action by action.

### 0.5 Optimistic UI and rollback

> **RULE ADM-2.** Every list/queue mutation (approve, reject, confirm, cancel, etc.) updates the local cache **optimistically** — the row moves out of the current queue view immediately on click, before the response returns — and **rolls back to the pre-action state** if the request errors with anything in §0.3's table. A rollback additionally shows the specific error toast from §0.3, not a generic "action failed". This applies uniformly across §§2–7 below and is not restated per action except where a screen's mutation is **not** safe to apply optimistically (called out explicitly — see §3's payment-recording action, which is deliberately **not** optimistic because a duplicated recording of cash received is spec 04's named worst-case, §2.6/§11.4 E-47).

- **Transition**: `NONE`
- **Guards**: `None`

### 1.3 Today's activity feed

A live-filtered view of the audit log (§6), scoped to `createdAtFrom = <start of today, UTC>` by default, with a namespace-appropriate role-scoping (spec 03 §11.7 — an `ADMIN` viewer of this feed does not see privileged provisioning rows; a `SUPER_ADMIN` sees everything, exactly as §6.3 below specifies for the full audit log viewer).

- **Endpoint**: `GET /api/admin/audit?createdAtFrom=<today>&sort=createdAt:desc` — **E-61**
- **Transition**: `NONE`
- **Guards**: `guardEntityIdRequiresEntityType` (inert here — no `entityId` filter is applied by default)
- **Filter**: `[Filter: All ▾]` maps to `entityType`/`action` query params, same DTO as the full Audit Log Viewer (§6.2) — this feed is the same endpoint pre-scoped to today, not a separate read model.
- **Empty**: "No activity yet today." — genuinely possible on a quiet morning; not treated as an error state.
- **Loading**: Row skeletons, 5 placeholder rows.
- **Error**: `400 VALIDATION_FAILED` is unreachable here (the dashboard constructs its own query, never a user-typed one) except through the `[Filter ▾]` control, in which case standard field-level handling applies. `401`/`403 ACCOUNT_INACTIVE`/`429`/`500` per §0.3.
- **"system" row**: the mock line in the wireframe above (`08:20 system …`) is deliberately shown crossed out / annotated, because **there is no `SYSTEM` actor anywhere in this platform** (spec 01 §Actor-classes: *"There is no `SYSTEM` actor class … Every status write in this system has a human actor"*; spec 04 §3.4: *"Nothing at all happens on a clock"*). This document includes that line only to make the point concrete for implementers — the real feed never renders such a row because no such `AuditLog` document can exist.

### 1.4 Quick-action queue

A cross-entity, priority-ordered feed of the single most actionable item from each hot queue — not a new endpoint, but a client-side merge of the top N rows from:

| Source | Endpoint | Action buttons shown |
|---|---|---|
| Oldest `PENDING_APPROVAL` listing | E-27 (`?moderationStatus=PENDING_APPROVAL&sort=createdAt:asc&limit=1`) | Approve (§2.2), Reject (§2.2), Details |
| Oldest `REQUESTED` booking | E-37 (`?status=REQUESTED&sort=createdAt:asc&limit=1`) | Confirm (§3.2), Reject (§3.2), Details |
| A `CONFIRMED` booking whose `startDate` is today | E-37 (`?status=CONFIRMED&startDateFrom=<today>&startDateTo=<tomorrow>&limit=1`) | Start handover → (opens §3.3's full handover flow — never a one-click action, because it requires `odometerOut` and the identity-check fields) |
| Oldest open `CANCELLATION_REQUESTED` | E-37 (`?status=CANCELLATION_REQUESTED&sort=createdAt:asc&limit=1`) | Resolve → (§3.2) |

**OPEN QUESTION ADM-OQ-4**: whether this composite view should be a single new backend endpoint (`GET /api/admin/dashboard/quick-actions`, **NEW**) that returns the merged, priority-ranked list server-side, versus four parallel client-side calls as tabled above. Four parallel calls is simpler and reuses existing endpoints exactly as specified; a single endpoint is one round trip and lets the server own the priority ordering (which item is "most urgent" is itself a judgement call — is an overdue return more urgent than a same-day handover? This document does not decide that ranking and assumes the four-list, fixed-order composition above pending a product decision). This document **defaults to the four-parallel-call approach** since it requires no new endpoint and every constituent call is already fully specified.

- **Empty**: "Nothing needs your attention right now." shown once all four source lists are confirmed empty (not while any is still loading — see below).
- **Loading**: Each of the four rows shows its own skeleton independently; the panel does not wait for all four before rendering any.
- **Error**: A failure on any one of the four source calls removes only that row (with a small inline retry icon), never blanks the whole panel — this is the one place in the dashboard where a partial failure must degrade gracefully rather than surfacing a page-level error, since the four sources are independent.

### 2.3 Approve

- **Endpoint**: `POST /api/admin/listings/:carId/approve` — **E-29**
- **Transition**: `Car.moderationStatus: PENDING_APPROVAL → APPROVED` (spec 01 §2.3, `actorClass: ADMIN`)
- **Guards**: `guardListingComplete` (re-checked at approval — content may have changed since submission), `guardRegistrationUniqueAmongModerated` (design D3 — the plate-uniqueness check that matters is at approval time, not creation)
- **Body**: `{ note?: string ≤500 }` — **[server-optional, UI-required per RULE ADM-1]**
- **What the admin is verifying, per spec 04 §3.2** (rendered as an on-screen checklist above the confirm button, not merely implied): photos are of the actual car, not stock images; the registration number matches the plate visible in the photos; the price is plausible; the description contains no contact details, external links, or anything indicating a sale. *"The admin is expected to check the plate against the owner's registration document, shown offline"* (design D3) — this is a human act the UI cannot verify and must not claim to.
- **Side effect**: `approvedBy`, `approvedAt` set. **`listingState` is unchanged** — approval is not publication (spec 02 §11.1: *"Approve and publish are deliberately separate"*). The confirm modal states this explicitly ("This approves the listing's content. It will not appear publicly until you also Publish it.") so an admin does not believe approval alone made the car live.
- **Confirmation modal**: title "Approve this listing?", body restates the not-yet-public note above, optional-but-UI-required note field, `[ Cancel ] [ Approve ]`.
- **Empty/Loading**: N/A (single-record action from the detail view or a queue row).
- **Error**: `409 INVALID_TRANSITION` (already `APPROVED`/`REJECTED` — e.g. two admins working the same queue) → "Someone else already reviewed this listing" toast, row removed from the queue per RULE ADM-2's rollback (not restored — the record genuinely moved). `409 GUARD_FAILED` (`guardListingComplete`, `details.missing[]`) → "Cannot approve — missing: {fields}" naming the exact fields, with a link to view the listing's raw data (no edit-in-place from the admin side; the owner edits their own listing). `409 CONFLICT { field: "registrationNumber" }` → "This registration number is already claimed by another listing" with a link to the conflicting record if the admin's role can see it (it can — admin visibility is unrestricted per spec 02 §7.1). Standard cases per §0.3.

### 2.4 Reject with reason

- **Endpoint**: `POST /api/admin/listings/:carId/reject` — **E-30**
- **Transition**: `Car.moderationStatus: PENDING_APPROVAL → REJECTED` (`actorClass: ADMIN`)
- **Guards**: `None beyond the edge`
- **Body**: `{ reason: string (1..500) }` — **[server-required]**
- **Side effect**: `rejectionReason`, `rejectedBy`, `rejectedAt`. The owner sees `rejectionReason` but never `rejectedBy` (spec 02 §7.2/§11.1) — the admin UI's confirmation modal states this ("The owner will see your reason text, not your name") so an admin does not write a reason as if addressing a colleague.
- **Confirmation modal**: mandatory (server-enforced, not just RULE ADM-1) reason textarea; `[ Cancel ] [ Reject listing ]`.
- **Error**: `400 VALIDATION_FAILED` (empty reason) → submit disabled until non-empty, matching server behaviour exactly (no client/server mismatch possible here, unlike the optional-note cases). `409 INVALID_TRANSITION` → same handling as §2.3. Standard cases per §0.3.

### 2.5 "Request changes" — reconciled against the model

**OPEN QUESTION ADM-OQ-5.** The brief lists "Request changes" as a third action alongside Approve and Reject. **No such state or endpoint exists anywhere in specs 01–04.** The `Car` moderation state machine (spec 01 §2.3, unchanged by spec 04 on this point) has exactly two outcomes from `PENDING_APPROVAL`: `APPROVED` or `REJECTED`. There is no `CHANGES_REQUESTED` state, and adding one would be a new spec 01 amendment (a new enum value, a new edge, a new `AuditLog` action), not something this document can introduce unilaterally.

This document's resolution: **"Request changes" is UI framing over the existing `REJECTED` transition (§2.4), not a new state.** The admin UI presents two reject-flavoured buttons that both call **E-30** with the same `{ reason }` body:

- `[ Reject — cannot approve ]` — a hard reject, framed to the owner as final content unacceptable as-is.
- `[ Request changes ]` — the *same* API call, with the reason textarea pre-seeded with actionable-change framing ("Please fix: …") — cosmetically distinguished client-side only, e.g. a stored client-side tag on which button was clicked, **never persisted server-side** since `Car.rejectionReason` is a single free-text field with no `kind` discriminator.

Both produce `moderationStatus: REJECTED`, both use the identical `REJECTED → PENDING_APPROVAL` resubmit path (**E-11**, owner-side) to return to the queue, and both write the identical `CAR_REJECTED` audit action. **If "request changes" needs to be genuinely distinguishable later** (e.g. for a dashboard split of "hard rejects" vs. "change requests"), that requires a spec 01 amendment adding a `rejectionKind` field or a new state — flagged here, not implemented.

### 2.6 Set availability (AVAILABLE_FOR_RENT / ON_HOLD) — reconciled against the model

**OPEN QUESTION ADM-OQ-6 — terminology mismatch.** `AVAILABLE_FOR_RENT` and `ON_HOLD` are not values anywhere in the resolved model. Design D2 deleted `Car.status`'s `AVAILABLE`/`RENTED` values entirely and replaced them with `moderationStatus` + `listingState`, and availability itself is **derived, never stored** (spec 04 §1.0: *"Availability is never a field on `Car`. There is no `AVAILABLE` and no `RENTED` status. Availability is derived, always, from `BookingDayLock`"*). This document cannot introduce a stored `AVAILABLE_FOR_RENT`/`ON_HOLD` field without directly contradicting D5, which spec 04 calls *"the single most load-bearing decision in the document"*.

This document's resolution — mapping the brief's two-state toggle onto the two real, independent mechanisms that together produce the same operator-visible effect:

| Brief's term | Closest real mechanism | Endpoint |
|---|---|---|
| `AVAILABLE_FOR_RENT` | `listingState = LISTED` (car is on the public market; day-by-day bookability is separately derived from locks) | `POST /api/admin/listings/:carId/publish` (**E-31**, from `UNLISTED`) or `.../relist` (**E-33**, from `DELISTED`) |
| `ON_HOLD` | The car **stays** `LISTED` (still visible, still browsable — spec 04 §1.2: *"a car is never 'hidden because it is rented'"*) but every day in an admin-chosen window is locked via an `ADMIN_BLOCK` (§4 below), making it unbookable for that window without touching `listingState` at all | `POST /api/admin/listings/:carId/availability-blocks` (**E-34**) |

The admin UI presents this as a single toggle control on the listing detail view, but it drives two different endpoints depending on which "hold" is meant:

```
Availability:  ( ) Available for rent   ( ) On hold
                                          └─ opens: [ From ][ To ][ Reason ] → E-34
```

**A genuinely *indefinite* "on hold" (no end date) is not representable.** E-34's `createAvailabilityBlockDto` requires both `from` and `to`, bounded to a ≤365-day span (spec 02 §11.2). An operator wanting a car off the calendar indefinitely must pick an end date (renewable by creating a new block when it lapses) — there is no "hold until further notice" primitive, consistent with spec 04 §3.4's *"nothing at all happens on a clock"* (an unbounded hold would need something to eventually un-hold it, and nothing in this platform runs on a schedule). **OPEN QUESTION ADM-OQ-7**: should an "indefinite hold" UI affordance exist at all, defaulting to some long-but-bounded window (e.g. 365 days, the maximum E-34 allows) with a visible expiry the admin must consciously renew? This document assumes **yes**, defaulting the "On hold" date picker to `today + 365d` when no end date is chosen, but flags this as a UI convention layered over a hard API limit, not a spec-level "indefinite" concept.

- **Endpoints**: E-31 / E-33 (listing state) and E-34 (date block) — see §2.3/§2.4 style tables above for E-31/E-33's own transition+guard rows, reused verbatim; E-34's full action table is in **§4.2**, not repeated here.
- **Toggle-specific empty/loading/error**: switching the radio optimistically flips the toggle's visual state (RULE ADM-2); on `409 GUARD_FAILED` from `guardModerationApproved` (attempting to publish/relist a car that isn't `APPROVED`) the toggle snaps back with "Cannot list — this car has not been approved" naming the current `moderationStatus`.

### 2.7 Flag/unflag, feature listing — reconciled against the model

**OPEN QUESTION ADM-OQ-8 — no spec authority.** Nothing in specs 01–04 defines a "flag" or "feature" concept for `Car`. There is no field, no endpoint, no guard, and no audit action anywhere in the read set for either. Spec 04 §8 (Reviews) has a moderation-relevant `HIDDEN`/`PUBLISHED` toggle, but that is scoped to the `Review` entity, not `Car`, and does not transfer.

This document does **not** silently invent authority for these two controls. It proposes them as **NEW**, to the same level of specification every other action in this document carries, exactly as spec 04 §8 did for the (also entirely additive) Reviews block:

**`Car.flagged`** (**NEW** field, `Δ-ADM-1`) — `{ flagged: boolean, flagReason?: string, flaggedBy?: ObjectId, flaggedAt?: Date }`. A flag is an **internal admin note**, never shown publicly and never itself a moderation state — a flagged car can still be `LISTED`. It exists to mark "needs a second look" (e.g. a borderline description, a suspicious price, a pattern of guest complaints) without forcing an immediate approve/reject decision.

| Endpoint | Method/path | Transition | Guards | Body |
|---|---|---|---|---|
| **E-91 — NEW** | `POST /api/admin/listings/:carId/flag` | `Car.flagged: false → true` — **not an entry in spec 01's `actorClass` table; this is a new, admin-only, non-status-machine field write, structurally like a note, not a `transition()` edge** | `None beyond the role gate` | `{ reason: string (1..500) }` — **[server-required]**, since an unexplained flag is exactly the kind of unauditable admin action spec 04 RULE BW-1 exists to prevent |
| **E-92 — NEW** | `POST /api/admin/listings/:carId/unflag` | `Car.flagged: true → false` | `guardAlreadyFlagged` **(NEW)** | `{ note?: string ≤500 }` — **[server-optional, UI-required per RULE ADM-1]** |

**`Car.featured`** (**NEW** field, `Δ-ADM-1`) — `{ featured: boolean, featuredBy?, featuredAt? }`. A featured car appears with priority placement on `/api/public/cars` (**E-06**) — **this requires E-06's response and sort behaviour to be extended, which is itself a spec 02 change, not something this admin-panel document can do unilaterally.** Featuring an unlisted or unapproved car must be refused (**OPEN QUESTION ADM-OQ-9**: should featuring require `moderationStatus = APPROVED AND listingState = LISTED`, mirroring the public-visibility predicate exactly? This document assumes **yes** — a featured `DRAFT` car is nonsensical — and proposes `guardCarPubliclyBookable`, already defined in spec 04 §3.1 P4, as the reused guard rather than inventing a new one).

|---|---|---|---|---|
| **E-93 — NEW** | `POST /api/admin/listings/:carId/feature` | `Car.featured: false → true` | `guardCarPubliclyBookable` (reused from spec 04 §3.1 P4) | `{ note?: string ≤500 }` — **[server-optional, UI-required]** |

**Audit**: `CAR_FLAGGED`, `CAR_UNFLAGGED`, `CAR_FEATURED`, `CAR_UNFEATURED` — all **new** `AuditLog.action` enum values, none currently in spec 01 §1.6's list (which the four `Δ-B9`-style deltas throughout spec 04 have already been extending piecemeal; this document's `Δ-ADM-1` continues that pattern rather than inventing a separate mechanism).

- **UI**: `[ Flag ▾ ]` on the listing detail view (§2.2) opens a small menu — "Flag for review" (E-91) / "Remove flag" (E-92, only shown when already flagged) — and a separate `[ Feature ]` / `[ Unfeature ]` toggle button, disabled with a tooltip ("Only approved, listed cars can be featured") when `guardCarPubliclyBookable` would fail.
- **Empty/Loading**: N/A (single-record toggle actions).
- **Error**: `409 GUARD_FAILED` (`guardCarPubliclyBookable`) on feature attempt → "Cannot feature — this car isn't currently live" toast, button stays disabled. `409 GUARD_FAILED` (`guardAlreadyFlagged`/`guardAlreadyFeatured`) → toast + UI re-syncs the toggle to its actual server state (defends against a double-click race). Standard cases per §0.3.

**Because E-91–E-94, `Car.flagged`, and `Car.featured` are entirely new, they require a spec 01 amendment (new `Car` fields) and a spec 02 amendment (new endpoints, new `AdminCar` fields) before implementation — consistent with `CLAUDE.md`'s "never modify specs while implementing." This document proposes them; it does not merge them.**

#### Approve booking → renter gains the godown pickup details

- **Endpoint**: `POST /api/admin/bookings/:bookingId/confirm` — **E-39**
- **Transition**: `Booking: REQUESTED → CONFIRMED` (spec 01 §2.4, `actorClass: ADMIN`)
- **Guards**: `guardStatusIsRequested`; `guardCarStillBookable` (`moderationStatus = APPROVED AND listingState = LISTED`); `guardRenterKycVerified` — **NOTE: this named guard is a spec 02 holdover from the pre-spec-04 model and no longer applies under spec 03/04's removal of KYC verification.** Spec 04 §3.1 replaces the request-time version of this check with P1–P11 (guardLicenceOnFile as an integrity assertion, guardNotOwnRental, guardDateRangeValid, guardNoExistingRequestForRange, guardOpenRequestCap, guardNoUnresolvedNoShow, guardNoOverdueRental, guardNoOverlappingRentalAnyCar), and at confirm time specifically the surviving re-checks are `guardRenterActive` and **`guardNoOverlappingRentalAnyCar` (P11, re-checked per `Δ-B22`)** — not a KYC re-verification, since there is nothing left to verify. This document uses the spec-04-correct guard set: `guardStatusIsRequested`, `guardCarStillBookable`, `guardRenterActive`, `guardDatesNotPast`, `guardNoOverlappingRentalAnyCar`; **`guardRenterKycVerified` is dropped entirely, consistent with `TR-22`'s assertion that no guard matching `/kyc|verif/i` may exist in the built system.**
- **Body**: `{ note?: string ≤500, overlapOverrideReason?: string (1..500) }` — `note` **[server-optional, UI-required]**; `overlapOverrideReason` is conditionally required only when `guardNoOverlappingRentalAnyCar` would otherwise fail and the admin deliberately overrides it (spec 04 §3.1 P11 — "a renter may legitimately book a second car for a family member").
- **What the admin verifies before clicking, per spec 04 §3.2** (again rendered as an on-screen checklist, not merely implied): the owner has been contacted out-of-band and agreed the car is genuinely free and they will be present at handover; the renter has been reached on their on-file phone number; the dates are operationally sensible; competing requests (shown above) have been reviewed and a decision made about which one wins.
- **Side effects (same transaction)**: insert one `BookingDayLock` (`source: BOOKING`) per day in `[startDate, endDate)`, plus `BUFFER` locks for `turnaroundBufferDays` if configured (spec 04 §1.5); `confirmedBy`, `confirmedAt` set. **`Car` itself is untouched — see §3.6 below for the explicit reconciliation of "car auto-set to RENTED_OUT", which does not apply here or anywhere in this model.**
- **Godown pickup disclosure, exactly**: per spec 04 §4.2 RULE GH-2, the **instant** this transition lands, the renter's `BookingDetail` (E-21) gains a `pickup: GodownInfo` block — the single godown's address, contact phone, and instructions, sourced from the `SystemConfig` singleton (spec 03 §11.8), never from `Car` or `User`. **No party's phone number is ever exposed to the other** — `PartyContact` never carries `phone`, in any status (spec 04 §4.1 RULE GH-1). This is not a separate action the admin UI performs; `pickup` is a derived consequence of `status = CONFIRMED`, evaluated fresh on every read. The confirm confirmation-modal states this instead: "Confirming will show the renter our pickup location and instructions. Neither party will see the other's phone number."
- **Confirmation modal**: the on-screen verification checklist above, `[ Cancel ] [ Confirm booking ]`.
- **Empty/Loading**: N/A (single-record action).
- **Error**: `409 GUARD_FAILED` (`guardCarStillBookable`) → "This car is no longer publicly listed" (e.g. the owner withdrew or delisted it between request and confirm). `409 CONFLICT { reason: "DATES_UNAVAILABLE", conflictingDays: [...] }` — **the D5 case, surfaced with the exact conflicting days highlighted on an inline mini-calendar**, since this is the single most consequential conflict in the platform (two admins racing to confirm overlapping requests — spec 04 §1.3: *"exactly one succeeds … the loser receives the 409"*). `409 GUARD_FAILED` (`guardNoOverlappingRentalAnyCar`, `details.bookingIds[]/carIds[]/overlappingDays[]`) → names the other booking(s) and offers the override field inline rather than a second round trip. Standard cases per §0.3.

#### Reject

- **Endpoint**: `POST /api/admin/bookings/:bookingId/reject` — **E-40**
- **Transition**: `Booking: REQUESTED → REJECTED` (`actorClass: ADMIN`)
- **Guards**: `guardStatusIsRequested`
- **Body**: `{ reason: string (1..500) }` — **[server-required]**
- **Side effects**: `rejectionReason`, `rejectedBy`. No locks to release — a `REQUESTED` booking never held any (spec 04 §5.2).
- **Confirmation modal**: mandatory reason. **This is also the endpoint used to clear a stale or conflicted `REQUESTED` booking per spec 04 §1.4** — the queue's "STALE"/"⚠" badges (§3.1) link directly into this action.
- **Error**: standard per §0.3, plus `409 INVALID_TRANSITION` when another admin already acted.

#### Mark offline payment received

- **Endpoint**: `POST /api/admin/payments` — **E-47**
- **Transition**: `Payment: — → PENDING`, **or `Payment: — → SETTLED` when `settledNow: true`** (design D7; **the `— → SETTLED` creation edge is flagged `BLOCKING` by spec 04 OQ-55 — see §9 below, this document assumes it lands before `PAY`/`ADM-UI` implementation begins**)
- **Guards**: `guardBookingExists`; `guardBookingExpectsPayment` (`status ∈ { CONFIRMED, CANCELLATION_REQUESTED, ACTIVE, COMPLETED, TERMINATED, NO_SHOW }`); `guardNotOverpaying` — **per-purpose** (spec 04 §6.1): `RENTAL` payments cap at `totalAmount`, `DEPOSIT` payments cap at `depositSnapshot`, unless `allowOverpayment: true`
- **Body**: `{ bookingId, amount: number > 0, paymentMethod: CASH|BANK_TRANSFER|UPI|CHEQUE|OTHER, purpose: RENTAL|DEPOSIT, referenceNote?, settledNow?: boolean, allowOverpayment?: boolean }`. **The brief's "amount, method (cash/UPI/bank transfer), reference number, optional receipt image" maps onto this exactly**, with one gap:

  **OPEN QUESTION ADM-OQ-11 — "optional receipt image" is not supported anywhere in the platform.** `Payment` (spec 01 §1.5, unamended by spec 04 on this point) has no image/attachment field, and spec 02 §2.1 states plainly: *"No `multipart/form-data` anywhere — image bytes are out of scope … the API accepts URLs only."* A receipt "image" would need the same treatment as `Car.images` — a URL, validated by a `guardImageUrlsAllowed`-style guard (spec 04 `Δ-B19` already repoints the old `guardDocumentUrlsAllowed` at `Car.images` specifically) — **and no such URL-producing upload flow exists anywhere in this platform for any entity** (spec 04 OQ-B1 flags this as still-blocking for `Car.images` itself). This document does **not** propose a `Payment.receiptImageUrl` field silently; it flags the gap and gives two options: **(a)** omit the receipt-image control entirely from this screen until an image-upload transport exists platform-wide (`docs/design/02`, per OQ-B1), or **(b)** add `Payment.receiptImageUrl?` (**NEW**, `Δ-ADM-2`) accepting a URL only, gated by the same `guardImageUrlsAllowed` guard, with the same caveat that no uploader produces such a URL yet. **This document assumes (a) for phase 1 — the field is absent from the form below — and marks (b) as a follow-on once image upload transport exists.**
- **Recording form (this document's UI, no receipt-image field per the resolution above)**:

  ```
  Record payment for Booking #6f2a
  Amount:        [ 3600        ]
  Purpose:       ( ) Rental   ( ) Deposit
  Method:        [ Cash ▾ ]  (Cash / UPI / Bank transfer / Cheque / Other)
  Reference:     [ optional — e.g. UPI txn id ]
  ☑ Settle immediately (cash received now)
  [ Cancel ]                              [ Record payment ]
  ```
- **Side effects (same transaction)**: when settled, `Booking.amountReceived += amount` (purpose `RENTAL`) or `Booking.depositReceived += amount` (purpose `DEPOSIT`) — written **only** by the Payment service (spec 04 §3.3, `TR-B3`).
- **NOT optimistic (deviation from RULE ADM-2, stated explicitly per §0.5)**: this action does **not** update the UI before the server responds. Spec 02 §2.5 names this the platform's one genuinely dangerous replay: *"a double-submitted cash entry inflates `amountReceived` and can let an unpaid car out"* (design D6). The submit button disables immediately on click and stays disabled until the response returns (success or error) — no optimistic row insertion into the payment ledger, no optimistic decrement of the "awaiting payment" dashboard tile.
- **Confirmation modal**: **not required for E-47 itself** — the form above already requires deliberate field entry and a Settle checkbox, which this document treats as its own confirmation step given the field's own guidance that a *second* modal on top of a full form is friction without added safety on the platform's most time-sensitive counter interaction. **OPEN QUESTION ADM-OQ-12**: does RULE ADM-1's blanket "every state-changing action gets a confirmation modal" apply here too, given `— → SETTLED` is itself a status transition? This document assumes **no** — the form itself is the confirmation — but flags the tension with RULE ADM-1's stated universality.
- **Error**: `409 GUARD_FAILED` (`guardBookingExpectsPayment`) → "This booking's status doesn't accept a payment right now" naming the current status. `409 GUARD_FAILED` (`guardNotOverpaying`, `details: { cap, alreadyReceived, attempted }`) → inline warning offering the `allowOverpayment` checkbox rather than silently blocking, since legitimate overpayment (a renter rounding up, a manual reconciliation) is a real case spec 04 explicitly allows with the flag. Standard cases per §0.3, **with the exception that `429 RATE_LIMITED` here specifically should never be silently retried by the client** (a retried cash-recording call is exactly the double-submit risk this whole action is built to avoid).

#### Activate (handover) — check passed

- **Endpoint**: `POST /api/admin/bookings/:bookingId/activate` — **E-41**
- **Transition**: `Booking: CONFIRMED → ACTIVE` (spec 01 §2.4, `actorClass: ADMIN`)
- **Guards**: `guardStatusIsConfirmed`; `guardPaymentCovered` (`amountReceived >= totalAmount`, overridable with `overrideReason`); `guardStartDateReached` (`today >= startDate`); `guardRenterActive` (spec 03 DEFECT-2 / `Δ-C4` — **the only remaining automated renter-side check on this path, now that KYC verification no longer exists**); `guardLocksIntact` (counts `source: BOOKING` rows only, per `Δ-B24`); `guardIdentityCheckPassed` (fails the whole call if `identityCheckPassed = false` — see §3.3's refused-handover path below); `guardIdentityCheckRecorded`; `guardMismatchRequiresNote` (conditionally, when the typed number does not match the record)
- **Body**: `{ odometerOut: number ≥ 0, identityCheckPassed: boolean [server-required, never defaulted], licenceNumberSeen: string (8..20, [A-Z0-9- ]) [server-required], identityCheckNotes?: string ≤1000, overrideReason?: string (1..500) }`
- **What is physically checked, per spec 04 §7.1 — the six checkboxes shown above plus the two the form renders as separate numeric/derived fields**:

  | # | Check | Rendered as |
  |---|---|---|
  | 1 | A physical licence is produced | Checkbox |
  | 2 | Licence number matches the record | Typed field, server-compared (`matchesRecord`, computed server-side, never submitted as a boolean by the client) |
  | 3 | Photo matches the person | Checkbox |
  | 4 | Name matches | Checkbox |
  | 5 | Not visibly expired | Checkbox |
  | 6 | Covers the vehicle class | Checkbox |
  | 7 | Is the named renter, not a collector | Checkbox |
  | 8 | Odometer read, fuel/damage noted | `odometerOut` field + free-text notes |
  | 9 | Cash counted | The "Amount received" line, cross-referenced against §3.2's payment-recording action, which must already have happened or be overridden here |

  **`identityCheck.passed` is one boolean standing for all of checks 1–7** (spec 04 §7.1/OQ-B34) — the six checkboxes above are **client-side UI scaffolding to make the admin actually look at each item**, not six separate server fields. Only the single `identityCheckPassed` boolean and the server-compared `licenceNumberSeen` are actually submitted. **This document assumes OQ-B34's stated resolution ("one attestation, presented as an on-screen checklist") and builds the form accordingly — the checklist is real UI, the boolean is the only thing sent.**
- **Server-side comparison, never client-side**: `matchesRecord = normalise(licenceNumberSeen) === normalise(User.drivingLicence.number)`, where `normalise` uppercases and strips spaces/hyphens (spec 04 §7.2). The admin never sees or types a "match: yes/no" — only the raw string, and the server decides. If `matchesRecord = false`, the **notes field becomes required** (`guardMismatchRequiresNote`) and the audit action changes to `BOOKING_STARTED_IDENTITY_MISMATCH` rather than plain `BOOKING_STARTED` — this is not shown to the admin as a different button, only as a required-notes prompt appearing inline once the mismatch is detected (client-side pre-check against the on-screen `drivingLicence.number`, confirmed authoritatively server-side).
- **No document upload anywhere on this screen** — `TR-B6` asserts server-side that `identityCheck` contains no field matching `/url|image|file|upload|scan|photo|doc/i`, and this document's form design matches that exactly: there is no "attach photo of licence" control, no camera capture, no file picker. This is the literal implementation of the user's stated platform constraint.
- **Payment-covered guard, rendered inline, not just as a post-submit error**: the "Amount received: ₹3,600 / ₹3,600 ✓" and "Deposit: ₹0 / ₹5,000 ⚠" lines are computed client-side from `AdminBookingDetail.amountReceived`/`totalAmount` and `.depositReceived`/`.depositSnapshot` *before* the admin clicks submit, so a shortfall is visible before the guard rejects it. **The deposit shortfall is advisory only and does not block submission** (spec 04 §6.2: *"the deposit is not part of the handover payment guard … only `amountReceived >= totalAmount` gates E-41"*) — the ⚠ is a warning glyph, not a disabled button.
- **Override path**: if `amountReceived < totalAmount`, submitting requires filling `overrideReason` (client-enforced the moment the shortfall is detected, mirroring the server's own conditional requirement) and the audit action becomes `BOOKING_ACTIVATED_UNPAID` rather than `BOOKING_STARTED` — again, this is `metadata`/audit-action behavior, not a different button.
- **Confirmation modal**: this entire form **is** the confirmation step (it cannot be meaningfully condensed into a yes/no dialog given the number of required fields) — RULE ADM-1 is satisfied by the form's own explicit submit action, not a second dialog on top of it.
- **Side effects (same transaction)**: `handedOverAt`, `odometerOut`, `identityCheck{…}`, `overrideReason?` written to `Booking`. **`Car` is untouched — see §3.6.**
- **Empty/Loading**: N/A (single-record form).
- **Error**: `409 GUARD_FAILED { guard: "guardPaymentCovered", details: { required, received, shortfall } }` → inline shortfall banner (already shown pre-submit) becomes a hard stop unless `overrideReason` is filled. `409 GUARD_FAILED { guard: "guardStartDateReached" }` → "This rental doesn't start until {date}" — handover cannot happen early. `409 GUARD_FAILED { guard: "guardRenterActive" }` → "This renter's account has been deactivated since this booking was confirmed — handover cannot proceed" with a link to §5 (User Management) to review why. `409 GUARD_FAILED { guard: "guardIdentityCheckPassed" }` → see the refused-handover flow immediately below; this is not a generic error toast, it routes to a dedicated screen. `409 GUARD_FAILED { guard: "guardMismatchRequiresNote" }` → notes field highlighted, submit re-enabled once filled. Standard cases per §0.3 otherwise.

#### If the check fails at handover

Per spec 04 §7.3 RULE ID-1 — *"A failed identity check never produces an `ACTIVE` booking. The car does not leave."* Selecting "Check failed" in the form above **does not submit E-41 at all**; it routes to a distinct action:

- **Endpoint**: `POST /api/admin/bookings/:bookingId/handover-refused` — **E-78**
- **Transition**: `NONE` if `outcome = HOLD` (stays `CONFIRMED`); `Booking: CONFIRMED → CANCELLED` (the same E-44 edge, same guards, same lock release) if `outcome = CANCEL`
- **Guards**: `guardStatusIsConfirmed`
- **Body**: `{ licenceNumberSeen?: string, reason: string (1..500) [server-required], outcome: 'HOLD' | 'CANCEL' }`
- **Form**:

  ```
  Handover refused — Booking #6f2a
  What happened? [ e.g. renter forgot their licence, mismatch, no-show at the door ]

  ( ) Hold — keep the booking CONFIRMED, they can come back today
  ( ) Cancel — this rental is not going ahead

  [ Cancel ]                                    [ Record refusal ]
  ```
- **Side effects**: `identityCheck` written with `passed: false`, `checkedBy`, `checkedAt`, `notes = reason`. If `CANCEL`: all locks released, `cancelledBy`, `cancellationReason = reason`.
- **Audit**: exactly one row — `BOOKING_HANDOVER_REFUSED` (`HOLD`) or `BOOKING_HANDOVER_REFUSED_CANCELLED` (`CANCEL`) (spec 04 §7.3: *"One call, one audit row"*).
- **Explicitly not a no-show**: this screen never offers "mark no-show" as an outcome of a failed handover, because the renter *did* turn up (spec 04 §7.3: *"Declaring a no-show would misrecord the event"*). No-show (§3.5 below) is only reachable from the booking-detail view for a `CONFIRMED` booking whose renter never appeared at all.
- **Error**: standard per §0.3; `400 VALIDATION_FAILED` (missing `reason`, or `outcome` absent) keeps the form open with inline errors.

### 3.4 Mark rental active / mark returned — "car auto-set" language, reconciled

**OPEN QUESTION ADM-OQ-13 — terminology mismatch, same root cause as §2.6.** The brief states "Mark rental active → car auto-set to `RENTED_OUT`" and "Mark returned/completed → car auto-set back to `AVAILABLE_FOR_RENT`". **Neither field exists.** Design D2 removed every booking-derived field from `Car` entirely — spec 04 §3.3 states this explicitly and by name: *"`Car` carries no booking-derived state at all. There is no `RENTED`, no `currentBookingId`, no `availableFrom`."* Confirming a rental active (§3.3's E-41) and completing it (E-42, below) touch **only** `Booking` and `BookingDayLock` — never `Car`. The *effect* the brief is describing — "this car is unavailable while it's out, and available again once it's back" — is real and correct, but it is produced entirely by the **presence or absence of `BookingDayLock` rows**, computed fresh on every availability read (spec 04 §1.2), not by a field flip on `Car`.

This document's resolution: the admin UI must **not** display any "Car status: RENTED_OUT" chip anywhere, because no such field exists to read. Instead, a car's current disposition is always rendered as a **derived** summary (e.g. "Currently on an active rental until 2026-10-04" or "Available" or "Blocked: maintenance until 2026-10-10"), computed from the same `AvailabilityResponse`/lock data the calendar screen (§4) already uses, cross-referenced with any `ACTIVE` booking. **This is a client-side presentation convention, not a new field**, and is called out here so implementers do not accidentally add a denormalised `Car.currentStatus` field to satisfy the brief's literal wording — doing so would recreate exactly the "second source of truth" problem spec 04 §3.3 and design §7 exist to prevent (*"exactly one service writes each denormalised field"* — and no service is chartered to write a booking-derived field onto `Car` at all, by design).

#### Complete (return)

- **Endpoint**: `POST /api/admin/bookings/:bookingId/complete` — **E-42**
- **Transition**: `Booking: ACTIVE → COMPLETED` (spec 01 §2.4, `actorClass: ADMIN`) — "mark returned/completed"
- **Guards**: `guardStatusIsActive`; `guardOdometerNotDecreasing` (`odometerIn >= odometerOut`)
- **Body**: `{ odometerIn: number ≥ 0, note?: string ≤500, lateReturn?: { lateDays, lateFeeAmount, note? }, conditionNote?: string }`
- **Form**:

  ```
  Complete rental — Booking #6f2a
  Odometer (in): [ 34580 ] km      (out was 34,210 — 370 km travelled)
  Condition notes: [ optional ]

  ⚠ This return is 2 days late.
    Suggested late fee: ₹2,400 (2 days × ₹1,200, spec 04 §2.3 — editable)
    Late fee to charge: [ 2400 ]      Note: [ optional ]

  Deposit decision is separate — you'll be prompted after this, per §3.5.

  [ Cancel ]                                    [ Complete rental ]
  ```
- **Late-return suggestion**: pre-filled from `AdminBookingDetail.lateReturnSuggestion { lateDays, suggestedLateFee, asOf }` (spec 04 §2.3, `Δ-B17`) — shown **only** when the booking is actually overdue; the suggestion is editable and the admin may enter `0` to waive it entirely (spec 04: *"the operator waives fees, negotiates, or charges a penalty rate as their business requires, and the system records the decision rather than making it"*).
- **Side effects (same transaction)**: delete all `BookingDayLock` rows for this booking (both `BOOKING` and `BUFFER` sources), then re-insert `BUFFER` rows for `[today, today+N)` best-effort; `returnedAt`, `odometerIn`; if `lateFeeAmount > 0`, `totalAmount += lateFeeAmount`. **Not payment-gated** — spec 04 §2.6: *"Completion is not gated on payment … A car that has come back is back."*
- **No deposit action here** — the deposit decision is a **separate, deliberate act** (spec 04 §6.3 RULE DP-2: *"never automatic and never part of `complete`"*) — see §3.5 immediately below, which the UI prompts for as a distinct next step rather than folding into this form.
- **Error**: `409 GUARD_FAILED { guard: "guardOdometerNotDecreasing" }` → "Odometer-in can't be less than odometer-out (34,210 km)" inline on the field. Standard cases per §0.3.

### 3.5 Deposit: mark received / mark returned / partial with damage notes

Fully specified by spec 04 §6.

#### Mark received (at handover, or earlier)

Uses the **same** `POST /api/admin/payments` (**E-47**) action as §3.2's "mark offline payment received", with `purpose: DEPOSIT` instead of `RENTAL`. This document does not duplicate the action table — see §3.2 above, substituting `purpose`. The handover screen (§3.3) surfaces the deposit-received figure inline; recording it can happen from either the handover form's "Amount received" line (linking out to this same E-47 call) or directly from the booking detail view.

#### Mark returned (full return)

- **Endpoint**: `POST /api/admin/payments/:paymentId/refund` — **E-50**, called against the original `DEPOSIT`/`IN` payment
- **Transition**: `Payment: — → PENDING` (or `SETTLED` with `settledNow`) on a **new** `direction: OUT`, `refundOf: <original>`, `purpose: DEPOSIT` record. **The original payment is never modified.**
- **Guards**: `guardRefundMatchesBooking`; `guardOriginalIsSettledIn`; `guardRefundNotExceedingOriginal`
- **Body**: `{ bookingId, amount: number > 0, paymentMethod, reason: string (1..500) [server-required], referenceNote?, settledNow?: boolean }`
- **Form (full return)**:

  ```
  Return deposit — Booking #6f2a
  Deposit held: ₹5,000
  Amount to return: [ 5000 ]     Method: [ Cash ▾ ]
  Reason: [ Car returned in order, no damage ]
  ☑ Settle immediately

  [ Cancel ]                                    [ Return deposit ]
  ```
- **Side effect**: `Booking.depositReturned += amount`.

#### Partial return with damage notes

- **Same endpoint** (E-50), with `amount < depositReceived` and a **mandatory** `deductions[]` array:

  ```ts
  deductions: [{ category: 'DAMAGE'|'FUEL'|'CLEANING'|'LATE_FEE'|'TRAFFIC_FINE'|'OTHER', amount: number > 0, note: string (1..500) }]
  ```
- **Guard**: `guardDeductionsReconcile` — `sum(deductions.amount)` must exactly equal `depositReceived − refundAmount` (spec 04 §6.4: *"the arithmetic must close … an unexplained retained balance is the exact shape of a dispute nobody can later resolve"*).
- **Form**:

  ```
  Return deposit (partial) — Booking #6f2a
  Deposit held: ₹5,000
  Amount to return: [ 3500 ]     Method: [ Cash ▾ ]
  Reason: [ Minor scratch on rear bumper ]

  Deductions (must total ₹1,500 — the retained amount):
  ┌─────────────┬────────┬────────────────────────────┐
  │ Category ▾  │ Amount │ Note (required)             │
  ├─────────────┼────────┼────────────────────────────┤
  │ DAMAGE      │ 1500   │ Rear bumper scratch, repair  │
  │             │        │ quote attached offline       │
  └─────────────┴────────┴────────────────────────────┘
  [ + Add deduction line ]
  Running total: ₹1,500 / ₹1,500 required ✓

  ☑ Settle immediately

  [ Cancel ]                                    [ Return deposit ]
  ```
- **`LATE_FEE` double-charge warning**: if this booking already has `lateFeeAmount > 0` (from §3.4's complete-rental late-fee entry) **and** the admin adds a `LATE_FEE` deduction line here, the UI shows a non-blocking warning banner ("This booking already has a ₹2,400 late fee added to the total — check you're not charging it twice") per spec 04 §6.4/`TR-B5`: *"not forbidden … but it must never be accidental."*
- **Side effect**: `Booking.depositReturned += amount`. `depositRetained` is **not** touched by a partial-with-refund call — see full retention below.

#### Full retention (no money returned)

- **Endpoint**: `POST /api/admin/bookings/:bookingId/retain-deposit` — **E-77**
- **Transition**: `NONE` (a money-ledger write, not a `Booking.status` transition)
- **Guards**: `guardBookingClosed` (`status ∈ { COMPLETED, TERMINATED, NO_SHOW, CANCELLED }`); `guardDepositHeld` (`depositReceived − depositReturned > 0`); `guardDeductionsReconcile` (`sum(deductions) = depositHeld`)
- **Body**: `{ deductions: [...], reason: string (1..500) [server-required] }`
- **Form**: identical shape to the partial-return deductions table above, but with **no** "Amount to return" field at all — the UI presents this as a visually distinct third option ("Retain full deposit — no refund") rather than a zero-amount E-50 call, because **E-50 explicitly rejects `amount: 0`** (spec 04 §6.4: *"An E-50 call with `amount: 0` is rejected"*) — this is why full retention is a structurally separate action, not the partial-return form with zero typed in.
- **Side effects**: `depositRetained = depositHeld`, `depositRetainedAt`, `depositRetainedBy`, `depositDeductions[]`. **Executed by the Payment service**, not the Booking service, despite the `/bookings/` path (spec 04 §3.3: *"a fourth writer for the deposit ledger, outside the one place that maintains it"* would otherwise result).
- **Error (all three deposit actions)**: `409 GUARD_FAILED { guard: "guardDeductionsReconcile", details: { retained, deductionTotal } }` → inline "Deductions must total ₹{retained} — currently ₹{deductionTotal}" under the running-total line, submit disabled until they match exactly. `409 GUARD_FAILED { guard: "guardOriginalIsSettledIn" }` → "No settled deposit payment found for this booking" (should be unreachable from the UI, since the button is only offered when `depositReceived > 0`, but handled defensively). Standard cases per §0.3.

### 3.6 Cancel / mark no-show with reason

#### Cancel (admin)

- **Endpoint**: `POST /api/admin/bookings/:bookingId/cancel` — **E-44**
- **Transition**: `Booking: REQUESTED → CANCELLED` **or** `CONFIRMED → CANCELLED` (spec 01 §2.4, `actorClass: ADMIN`)
- **Guards**: `guardStatusCancellable` (`status ∈ { REQUESTED, CONFIRMED }` — an `ACTIVE` booking must use Terminate, not Cancel)
- **Body**: `{ reason: string (1..500) }` — **[server-required]**
- **Side effects (same transaction)**: release **all** day-locks for this booking if any were held (a `CONFIRMED` booking's locks; a `REQUESTED` booking never held any); `cancelledBy`, `cancellationReason`.
- **Confirmation modal**: mandatory reason; when cancelling a `CONFIRMED` booking with `amountReceived > 0`, an additional non-blocking note: "This booking has ₹{amount} recorded as received. Cancelling does not refund it automatically — record a refund separately if needed" (spec 04 §5.3 RULE CN-1: *"Cancellation never moves money automatically"*).
- **Error**: `409 INVALID_TRANSITION { details: { from: "ACTIVE" } }` → "This rental is already active — use Terminate instead" with a direct link to the terminate action (spec 04 §5.1: an `ACTIVE` booking's only exit is `terminate`, E-43, not covered in the brief's literal list but included here for completeness since the UI must route an admin correctly rather than dead-ending on a disabled button with no explanation). Standard cases per §0.3.

#### Terminate (mid-rental, not in the brief's literal list but required for a complete Cancel flow)

Included because §3.6's Cancel action, correctly implemented, must redirect an `ACTIVE` booking here rather than silently failing:

- **Endpoint**: `POST /api/admin/bookings/:bookingId/terminate` — **E-43**
- **Transition**: `Booking: ACTIVE → TERMINATED` (design D4, `actorClass: ADMIN`)
- **Guards**: `guardStatusIsActive`; `guardEffectiveFromValid` — **redefined by spec 04 RULE PR-4 to `[startDate, today]`, not spec 02's original `[startDate, endDate)`** — the original definition strands every overdue rental with no legal `effectiveFrom` at all (spec 04 §2.3: *"the booking is stranded in `ACTIVE` with its day-locks held forever"*); this document uses the corrected guard.
- **Body**: `{ reason: string (1..500) [server-required], odometerIn?: number ≥ 0, effectiveFrom?: YYYY-MM-DD (defaults to today) }`
- **Side effects**: locks released from `effectiveFrom` forward only (not the whole booking — days already elapsed are past and irrelevant); `terminatedAt`, `terminationReason`, `odometerIn` if given.

#### Mark no-show

- **Endpoint**: `POST /api/admin/bookings/:bookingId/no-show` — **E-46**
- **Transition**: `Booking: CONFIRMED → NO_SHOW` (design D4/spec 04 `Δ-B8`, `actorClass: ADMIN`)
- **Guards**: `guardStatusIsConfirmed`; `guardStartDatePassed` (`today > startDate` — a no-show cannot be declared before the renter was due)
- **Body**: `{ reason?: string ≤500 }` — **[server-optional, UI-required per RULE ADM-1]**
- **Side effects (same transaction)**: release all day-locks — spec 04 §5.4: *"the car is free the same day"*; `noShowAt`, `noShowBy`, `noShowReason?`, `noShowCleared = false`.
- **The strike**: setting `noShowCleared = false` triggers spec 04 §3.1 guard P9 (`guardNoUnresolvedNoShow`) — **while this flag is `false`, the renter cannot request any new booking anywhere on the platform.** The confirmation modal states this consequence explicitly: "This will block {renter name} from making new booking requests until an admin clears this strike."
- **Clearing a strike**:

  - **Endpoint**: `POST /api/admin/bookings/:bookingId/clear-no-show` — **E-76**
  - **Transition**: `NONE` — `status` stays `NO_SHOW`; only `noShowCleared: false → true`
  - **Guards**: `guardStatusIsNoShow`; `guardNotAlreadyCleared`
  - **Body**: `{ reason: string (1..500) }` — **[server-required]** — spec 04 §5.4: *"without E-76 a single no-show is a permanent, unappealable ban … disproportionate."*
  - **Where this lives in the UI**: on the booking's detail view once `status = NO_SHOW`, and additionally surfaced on the User Management screen's booking-history tab (§5.2) so an admin reviewing a renter's record can clear a strike from that context without navigating back to the individual booking.
- **Error (no-show)**: `409 GUARD_FAILED { guard: "guardStartDatePassed" }` → "This booking's start date ({date}) hasn't passed yet — a no-show can't be declared before then." Standard cases per §0.3.

## 4. Availability control

### 4.1 Wireframe — master calendar across all cars

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Calendar          [Car: All ▾]  ◀ September 2026 ▶        [+ Block dates]│
├──────────────────────────────────────────────────────────────────────────┤
│               Mon  Tue  Wed  Thu  Fri  Sat  Sun                          │
│ Honda City    ░░░  ░░░  ▓▓▓  ▓▓▓  ▓▓▓  ░░░  ░░░                          │
│ Maruti Swift  ░░░  ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓  ░░░   ▓ = BookingDayLock,   │
│ Toyota Innova ▒▒▒  ▒▒▒  ▒▒▒  ░░░  ░░░  ░░░  ░░░     any source           │
│                                                       ▒ = ADMIN_BLOCK    │
│  Click any locked cell → shows source, and bookingId/reason if admin    │
└──────────────────────────────────────────────────────────────────────────┘
```

- **Endpoint (per car row)**: `GET /api/admin/listings/:carId/availability` — **E-36**
- **Transition**: `NONE`
- **Guards**: `None`
- **Query**: `from`, `to` (both required, ≤365-day window — wider than the public E-08's 180-day cap, since an admin has an operational reason to see further out)
- **Response**: `AvailabilityResponse & { blockedRanges: [{ from, to, source, bookingId?, blockId?, reason? }] }` — **the admin variant discloses `source`/`bookingId`/`blockId`/`reason` per cell**, unlike the public calendar (E-08), which shows only that a day is blocked, never why (spec 04 §1.2: *"an admin querying availability … each blocked range additionally carries `source`, `bookingId?`, `blockId?`, `reason?`. This is the only place the reason for a blocked day is disclosed"*).
- **A car with a `CONFIRMED` booking is still shown fully in the grid, not hidden** — spec 04 §1.2's explicit consequence: *"a car with a `CONFIRMED` booking is still `LISTED` and still appears in public search. Only the specific days are unavailable. A car is never 'hidden because it is rented'."* The calendar UI must not offer any control that removes a car from this grid based on its booking activity — only `listingState` (below) removes a car row, and even then it should arguably still render greyed rather than vanish, so an admin scanning the whole fleet does not lose track of delisted cars with lingering obligations. **OPEN QUESTION ADM-OQ-14**: should a `DELISTED` car still appear (greyed) on this master calendar if it holds a `CONFIRMED`/`ACTIVE` booking (spec 04 §3.3: delisting does not release locks or end an active rental)? This document assumes **yes, greyed with a "delisted" badge**, since hiding it entirely would make an admin lose visibility of an obligation that still exists.
- **Per-car row query strategy**: this document does not assume a single "all cars, all days" endpoint exists — none does. The master calendar is built by the client issuing E-36 once per visible car row for the visible date window, in parallel. **OPEN QUESTION ADM-OQ-15**: at fleet scale this is N parallel requests per calendar render; spec 04 OQ-B35 raises exactly this shape of concern for a different screen (per-row aggregation cost) without resolving it. A batched `GET /api/admin/availability?carIds[]=...&from=...&to=...` (**NEW**, not proposed with a number since this document does not commit to it) may be needed before this screen is viable past a small fleet — flagged, not built.
- **Empty**: "No cars to show" only if the fleet itself is empty (vanishingly unlikely for an admin panel in use) — otherwise every car row always renders, empty of shading, meaning fully available.
- **Loading**: Each car row loads independently (skeleton bar) rather than blocking the whole grid on the slowest row.
- **Error**: `400 VALIDATION_FAILED` (window > 365 days) → date-range picker clamps and re-issues rather than surfacing a raw error. `404` (a car deleted mid-session) → that row is removed with a note. Standard cases per §0.3 otherwise.

### 4.2 Toggle car availability

Reconciles to the same two-mechanism split already established in §2.6 — repeated here in the availability-control context rather than cross-referenced only, since the brief lists it as a distinct bullet under this screen:

| Toggle | Mechanism | Endpoint |
|---|---|---|
| Publish / take off market entirely | `listingState: UNLISTED/DELISTED → LISTED` or `LISTED → DELISTED` | **E-31** / **E-33** (publish/relist) and **E-32** (delist) |
| Block specific dates without delisting | `BookingDayLock { source: ADMIN_BLOCK }` insert/delete | **E-34** / **E-35** (§4.3 below) |

- **Delist, admin-initiated, overridable over a live rental** (distinct from the owner's own non-overridable delist, E-13):
  - **Endpoint**: `POST /api/admin/listings/:carId/delist` — **E-32**
  - **Transition**: `Car.listingState: LISTED → DELISTED` (`actorClass: ADMIN`)
  - **Guards**: `guardNoLiveRental` — **overridable** with `force: true` (unlike the owner's own E-13, which cannot be forced) — spec 02 §11.1: *"An admin delisting a car with an `ACTIVE` rental is a real scenario (stolen vehicle, safety recall, fraud)"*.
  - **Body**: `{ reason: string (1..500) [server-required], force?: boolean }`
  - **Confirmation modal**: standard reason-required modal; when `force` would be needed (an `ACTIVE`/future-`CONFIRMED` rental exists on this car), the modal shows the blocking booking id(s) and a separate, visually distinct confirmation step for the forced variant ("This car has an active rental. Delisting will NOT end that rental — you must still Complete or Terminate it separately.") so an admin cannot mistake a forced delist for ending the rental itself.
  - **Audit**: `CAR_DELISTED`, or `CAR_DELISTED_FORCED` when `force: true` — a distinct, separately-greppable action name (spec 02 §11.1).
  - **Error**: `409 GUARD_FAILED { guard: "guardNoLiveRental", details.bookingIds[] }` → names the blocking booking(s) with links, offers the `force` checkbox inline. Standard cases per §0.3.

### 4.3 Block dates (maintenance, owner personal use)

- **Endpoint**: `POST /api/admin/listings/:carId/availability-blocks` — **E-34**
- **Transition**: `NONE` on `Car` — creates `BookingDayLock` rows, does not move any entity's status
- **Guards**: `guardDateRangeValid`; `guardNoConflictingLocks` (enforced by the unique `{ car, day }` index inside the transaction, not a pre-read — this is the same D5 mechanism that arbitrates double-booking, applied uniformly, per spec 04 §1.1: *"The unique index arbitrates every collision uniformly … There is exactly one code path"*)
- **Body**: `{ from: YYYY-MM-DD, to: YYYY-MM-DD, reason: string (1..500) [server-required], force?: boolean }`
- **Form**:

  ```
  Block dates — Honda City
  From: [ 2026-10-10 ]   To: [ 2026-10-17 ]
  Reason: [ Scheduled service — brake pads ]

  [ Cancel ]                                       [ Block dates ]
  ```
- **Side effect on success**: one `ADMIN_BLOCK` lock row per day in `[from, to)`, all sharing a generated `blockId`, in one transaction.

### 4.4 Conflict warning when blocking dates with existing bookings

Full behaviour per spec 04 §1.6–§1.7, RULE AV-4: *"A block never changes a booking's status."*

| Scenario | UI behaviour |
|---|---|
| Every day in range is free | Block created immediately, no warning. |
| Days locked by a `CONFIRMED`/`ACTIVE` booking, no `force` | `409 CONFLICT { reason: "DAYS_ALREADY_LOCKED", conflictingDays, conflictingBookingIds }` → modal lists the exact conflicting days and links each to its booking; offers `[ Force block the free days ]` (sets `force: true` and resubmits) or `[ Cancel and deal with the booking(s) first ]`. |
| `force: true`, conflicts are all `BOOKING`/`BUFFER` | `201`, response carries `{ blockId, blockedDays, skippedDays, skippedBookingIds }` — **the block is created only on the free days; the booking-locked days are silently skipped, not overridden.** UI shows a non-error success banner: "Blocked {N} of {M} requested days. {K} days were skipped because {bookingId} holds them." Audited as `CAR_AVAILABILITY_BLOCKED_PARTIAL`. **The booking itself is untouched — no cancel, no notification to the renter or owner beyond the operator's own out-of-band process.** |
| Days locked by another `ADMIN_BLOCK` | `409` always — `force` does **not** apply block-vs-block (spec 04 §1.7: *"two overlapping maintenance windows are an operator mistake"*). Modal: "These days are already blocked for another reason: {existing reason}. Remove that block first if this is a mistake." |
| Days are `BUFFER` rows, `force: true` | The buffer rows are **converted in place** to `ADMIN_BLOCK` (reversibly — `convertedFromBufferOf` set) rather than deleted-and-recreated. UI shows "This overlaps {N} days of automatic turnaround buffer after booking {id}. Blocking will use those days; they'll be restored automatically if you remove this block later." |
| An `ACTIVE` rental's days | Identical to the `CONFIRMED` row above — skipped, never overridden, because *"the car is physically with a renter; a calendar row cannot recall it"* (spec 04 §1.7). |

- **Removal**: `DELETE /api/admin/listings/:carId/availability-blocks/:blockId` — **E-35**
  - **Guards**: `guardBlockBelongsToCar` (mismatched car → `404`, never `409`, so the route cannot be used to probe another car's blocks — spec 02 §11.2); `guardBlockIsAdminOwned` (a `BOOKING`-source lock can never be deleted through this route)
  - **Reversal of a §1.7 buffer conversion**: if the deleted block's rows carry `convertedFromBufferOf`, those specific rows are **reverted to `BUFFER`, not deleted** — the booking gets its turnaround days back. The removal confirmation modal states this when applicable: "{N} of these days were converted from a booking's turnaround buffer and will be restored to it."
  - **Error**: `404 NOT_FOUND` (absent, or belongs to a different car) → "This block no longer exists" + calendar refresh. `409 GUARD_FAILED { guard: "guardBlockIsAdminOwned" }` → should be unreachable from this UI (the calendar never offers a delete control on a `BOOKING`-source cell), handled defensively with a generic error. Standard cases per §0.3.
- **Empty/Loading**: N/A for the block-creation form; the calendar grid's own empty/loading states are covered in §4.1.

### 5.3 Suspend / ban with reason

Per spec 03 §10.1: *"'ban' and 'suspend' are the same field … only the audited `reason` distinguishes them."* This document's UI presents one action, not two, consistent with that finding — a single `[ Suspend / Ban ]` button opens one modal, and the distinction between a temporary suspension and a permanent-feeling ban lives entirely in the free-text reason, never in a separate state.

- **Endpoint**: `POST /api/admin/users/:userId/deactivate` — **E-59**
- **Transition**: `User: isActive true → false` (spec 01 §2.1, `actorClass: ADMIN`)
- **Guards**: `guardNotSelf` (an admin cannot deactivate their own account); `guardNotLastAdmin` (counts `role ∈ { ADMIN, SUPER_ADMIN }`, spec 03 §1.5); `guardNotHigherPrivilege` (spec 03 §11.6 — an `ADMIN` cannot deactivate a `SUPER_ADMIN`; `SUPER_ADMIN` can deactivate anyone including another `SUPER_ADMIN`, peer action intentionally allowed)
- **Body**: `{ reason: string (1..500) [server-required], until?: YYYY-MM-DD }`
- **Form**:

  ```
  Suspend Priya N.
  Reason: [ Repeated no-shows — see booking history ]
  Until (optional, advisory only — see note below): [ 2026-10-01 ]

  This user will be logged out everywhere immediately. Their listed cars
  and confirmed bookings are NOT automatically cancelled — you'll need to
  handle those separately if this suspension should affect them.

  [ Cancel ]                                    [ Suspend account ]
  ```
- **`until` is advisory metadata only, not an enforced auto-expiry**: spec 03 §10.1 confirms spec 02 C-7/OQ-51's finding — *"an enforced `suspendedUntil` needs a scheduler or a check-on-read (neither exists)"* — so `until` is recorded in the audit `metadata` and shown back on this screen as a reminder, but **nothing automatically reactivates the account on that date.** The form's helper text makes this explicit rather than implying an auto-expiry the platform cannot deliver.
- **No cascade, explicitly stated in the form**: spec 03 §10.3 DEFECT-1 notes a suspended owner's `LISTED` cars stay listed and bookable, and their `CONFIRMED` bookings stay confirmed — this document's form surfaces that as a warning rather than silently leaving the admin to discover it later. **OPEN QUESTION ADM-OQ-16**, restating spec 03's own OQ-A22: should this action *also* force-delist the target's `LISTED` cars (via the existing forced-delist path, E-32 with `force: true`, audited as `CAR_DELISTED_FORCED`)? Spec 03 recommends yes; spec 02's original assumption was no cascade; **this document does not resolve the disagreement and does not silently pick one** — the form above reflects the current no-cascade behaviour and links out to §4.2's delist action as a manual follow-up step, pending that decision.
- **Side effects**: `isActive = false`; every `Session` of the target revoked immediately (spec 03 §4.5).
- **Error**: `409 GUARD_FAILED { guard: "guardNotSelf" }` → should be unreachable (an admin's own row does not offer this button in the UI), handled defensively. `409 GUARD_FAILED { guard: "guardNotLastAdmin" }` → "This is the last active admin account — deactivating it would lock the whole platform out. Promote another admin first." `409 GUARD_FAILED { guard: "guardNotHigherPrivilege" }` → "You don't have permission to suspend a Super Admin account" (only reachable by an `ADMIN` viewing a `SUPER_ADMIN`'s profile; the button should be disabled client-side for this combination, with the server guard as defense-in-depth). Standard cases per §0.3.

### 5.4 Reactivate

- **Endpoint**: `POST /api/admin/users/:userId/reactivate` — **E-60**
- **Transition**: `User: isActive false → true` (`actorClass: ADMIN`)
- **Guards**: `None`
- **Body**: `{ reason?: string ≤500 }` — **[server-optional, UI-required per RULE ADM-1]**
- **Does not restore sessions** (they were revoked and are not recoverable — spec 03 §10.5) and **does not relist cars** even under the OQ-A22 cascade recommendation — reactivation is deliberately the more conservative direction: *"relisting is a fresh admin decision (E-33)"*. The confirmation modal states both.
- **Error**: `409 INVALID_TRANSITION` (already active) → standard per §0.3.

## 7. Admin UX requirements

### 7.1 Bulk actions (approve multiple listings)

**No bulk endpoint exists anywhere in specs 01–04.** Every moderation action specified (E-29 approve, E-81 review-approve, etc.) operates on exactly one record. This document proposes a bulk-approve endpoint for listings, to the same standard of specification as every other action above:

- **Endpoint**: `POST /api/admin/listings/bulk-approve` — **E-95 — NEW**
- **Transition**: `Car.moderationStatus: PENDING_APPROVAL → APPROVED`, applied to each `carId` in the request, individually (`actorClass: ADMIN`, same edge as E-29, run N times under one API call)
- **Guards**: identical per-item guards to E-29 (`guardListingComplete`, `guardRegistrationUniqueAmongModerated`), evaluated **per car**, not once for the batch.
- **Body**: `{ carIds: ObjectId[] (1..50), note?: string ≤500 }`

**OPEN QUESTION ADM-OQ-17 — all-or-nothing vs. best-effort, the same shape of question spec 04 §1.6/§1.7 already answers for admin blocks.** Spec 04's own precedent for a batch operation that can partially fail is instructive: `POST .../availability-blocks` with `force: true` is explicitly **best-effort**, applying to whatever succeeds and reporting what was skipped, rather than aborting the whole call on one conflict (spec 04 §1.7: *"the block is created only on the free days … the response is `201` carrying `{ blockId, blockedDays, skippedDays, skippedBookingIds }`"*). This document recommends the **same best-effort shape** for bulk-approve, for the identical reason: an admin selecting 20 listings to approve should not have the other 19 blocked because one has since been edited into an incomplete state.

- **Recommended response shape**, following the admin-block precedent's pattern exactly: `{ approved: [carId, ...], failed: [{ carId, code, guard? }, ...] }`, `200 OK` even on partial failure (never a `409` for the whole call — a per-item guard failure is not a whole-request conflict).
- **Audit**: **one `CAR_APPROVED` row per successfully approved car** (spec 01 §1.6's one-row-per-transition rule applies per entity, not per API call — a bulk call is a batch of individual transitions, not itself a new kind of transition, consistent with how spec 04 treats every other multi-row write in this document, e.g. E-34's one-`blockId`-many-lock-rows shape still audits as a single row *because it is genuinely one lock-set creation*, whereas approving 20 unrelated cars is genuinely 20 separate moderation decisions and must read as 20 rows in the audit log, not one hiding the other 19). **OPEN QUESTION ADM-OQ-18**: should a bulk call additionally write one summary `CAR_BULK_APPROVED` row referencing all the individual ones, purely for "an admin ran a bulk action at this time" discoverability? This document assumes **no** — the individual rows are sufficient and a summary row risks double-counting in any report keyed on `CAR_APPROVED`, the exact failure mode spec 04 repeatedly warns against for `settledNow` (E-47) and `handover-refused` (E-78).
- **UI**:

  ```
  ┌──────────────────────────────────────────────────────────────────┐
  │  Listings                       [Bulk ▾: 3 selected]              │
  ├──┬──────────────────────────────────────────────────────────────┤
  │☑ │ Honda City 2021 …                                              │
  │☑ │ Maruti Swift 2019 …                                            │
  │☑ │ Toyota Innova 2020 …                                           │
  ├──┴──────────────────────────────────────────────────────────────┤
  │  [ Approve selected (3) ]     [ Clear selection ]                 │
  └──────────────────────────────────────────────────────────────────┘

  → confirmation modal:
  ┌──────────────────────────────────────────────────────────────────┐
  │  Approve 3 listings?                                              │
  │  Honda City 2021, Maruti Swift 2019, Toyota Innova 2020           │
  │  Note (optional, applied to all): [                            ]  │
  │  [ Cancel ]                              [ Approve all 3 ]        │
  └──────────────────────────────────────────────────────────────────┘

  → result, if partial:
  ┌──────────────────────────────────────────────────────────────────┐
  │  ✓ 2 approved     ✗ 1 failed                                      │
  │  Maruti Swift 2019 — missing: rentalPricePerDay      [ View → ]  │
  └──────────────────────────────────────────────────────────────────┘
  ```

- **Optimistic UI, adapted for bulk**: per RULE ADM-2, all N selected rows leave the queue optimistically on submit; on the partial-failure response, the `failed[]` rows are **re-inserted** into the queue (not silently dropped) with their specific error shown inline, while `approved[]` rows stay removed.
- **This endpoint, `E-95`, is entirely new and requires a spec 02 amendment before implementation** — same status as §2.7's E-91–E-94.

## 10. Out of scope for this document

- **Everything spec 04 §12 already excludes from the platform** (sale/resale, payment gateways, online identity verification, insurance, damage beyond the deposit, fuel policy, mileage limits, multi-car bookings, dynamic pricing, coupons, owner payouts, tax/invoicing, two-sided reviews, external notification transport, scheduled jobs, geo search, multi-currency) is equally out of scope for the admin panel built on top of it. No screen in this document offers a control for any of these.
- **The renter-facing and owner-facing client applications.** This document specifies only the `/api/admin` (and `/api/superadmin`, where referenced) surface. The public browsing site and the owner's "my listings"/"my bookings" self-service screens are a separate `CL` block deliverable.
- **The `SUPER_ADMIN`-only Admins and Config screens**, beyond the pointer in §7.6 (see ADM-OQ-19).
- **Mobile/responsive layout for the admin panel.** Every wireframe in this document assumes a desktop-width operator console, consistent with spec 03 §4.1's finding that there is *"a single first-party browser client and no mobile app in scope"* — this document assumes that applies to the admin surface at least as strongly as the consumer one, since queue processing with keyboard shortcuts (§0.6) is not a touch-first interaction pattern.
- **Real-time/live-updating queues.** No WebSocket or SSE exists anywhere in this platform (spec 02 §15); every queue in this document is poll- or manual-refresh-based, consistent with spec 04 §9.1's *"nothing is pushed to any channel"* finding for the consumer side, applied identically here.
